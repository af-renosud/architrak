---
name: Supplier handoff integrity
description: Integrity rules for on-demand ArchiDoc supplier certificate data across seal and dispatch.
---

Supplier certificate creation uses the on-demand ArchiDoc handoff as its authoritative payment input. Sealing must use one explicit-date handoff snapshot for source-bank comparison, protected-RIB verification, rendering, and immutable evidence; never refetch independently between those steps. Dispatch must compare current handoff identity, date, and full content digest with the sealed evidence and require reissue on divergence. Keep the project rollout gate server-side and invisible rather than removing it from the safety boundary. If ArchiDoc replaces an opaque payment-supplier identity, rebind the existing canonical supplier before applying the authoritative bootstrap; an ID-keyed upsert alone can create a duplicate partner instead of rotating identity in place. If a duplicate already exists, preserve the referenced original and remove only a proven zero-reference duplicate before rebinding.

**Why:** Independent handoff fetches can observe different banking or RIB versions, causing invoice evidence to be validated against one payment instruction while another is issued or sent. Hiding rollout mechanics from users does not authorize removing the production kill switch. Opaque IDs are immutable strings within one publication but may be replaced upstream; treating the replacement as a new local supplier duplicates an existing business partner.

**How to apply:** Any supplier preview/create/seal/send change must carry one explicit issue date, reuse the same handoff within an issuance operation, keep protected values out of browser/log output, and preserve the sealed-history rollout bypass without bypassing live identity, source, amount, or digest checks. For an upstream identity correction, resolve the exact opaque ID from the strict authenticated feed, refuse numeric/derived IDs, lock and update exactly one existing supplier, reject collisions, then bootstrap and prove one canonical row remains. Before deleting a duplicate, enumerate inbound foreign-key references inside the same transaction; never discard the referenced business row merely because a newer row is active.
