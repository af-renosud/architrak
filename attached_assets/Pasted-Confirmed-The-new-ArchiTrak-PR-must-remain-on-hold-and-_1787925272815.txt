Answers to the reconciliation questions
Why was the canonical-partner model changed?
It should not have been changed. The new PR was developed from an outdated ArchiTrak checkout and I incorrectly interpreted “ff_suppliers is ArchiDoc’s canonical supplier master” as requiring a separate ArchiTrak supplier model. That overlooked the countersigned design where ArchiTrak represents the supplier in its existing canonical partner/contractor mirror with partnerType: "supplier". This was an incorrect architectural inference.

Does ArchiDoc still emit the agreed supplier-payment-readiness.v1 contract?
Yes at the code and fixture level. The ArchiDoc producer tests passed against the frozen supplier-payment-readiness.v1 fixture, and the fixture copied into the proposed PR was byte-identical to ArchiDoc’s fixture.
I did not perform a live production endpoint call, so I am not claiming independent runtime verification of the published endpoint.

Is the supplier ID the same immutable ID used by the existing ArchiTrak mirror?
Yes. The feed’s supplier.id is the immutable ArchiDoc supplier identity. It should populate the existing ArchiTrak canonical mirror identity—not create a second identity namespace or parallel supplier master.

Can the banking, verification, protected RIB, and assignment fields be added without replacing the released architecture?
Yes. They can and should extend the existing canonical supplier mirror where partnerType: "supplier", while preserving:

the existing immutable ArchiDoc supplier ID;
migrations 0115 and 0116;
existing quotation and supplier-certificate workflows;
contractor behavior for partnerType: "contractor".
A separate payment-supplier mirror and separate supplier quotation architecture are not required merely to consume the additional readiness fields.
