# PRD Specification: French Private Construction Billing & MOE Workflows
### Context for the Coding Agent
You are building the backend relational logic and workflow engine for a French BTP (construction) project management tool used by Architects/MOEs. The tool does **not** generate contractor invoices; instead, it acts as the clearinghouse. Contractors submit claims (*Demandes de paiement / Situations*), the Architect reviews and amends them, and the system generates a **Certificat de Paiement** (Payment Certificate) authorizing the Client (*Maître d'Ouvrage / MOA*) to pay.
## 1. Required Relational Data Model (Architecture Checklist)
Ensure the database schema supports this exact hierarchy:
 * **Project**: The overarching construction project.
 * **Lot**: A specific trade package within the project (e.g., Lot 03 - Plastering).
 * **Contractor**: The company assigned to a Lot.
 * **Marché de Travaux (The Parent Contract)**:
   * Replaces the *Devis* once signed.
   * Stores the definitive initial contract amount (Excluding VAT and Including VAT).
   * Must support Avenants (Amendments) which modify the total contract value over time.
   * *Flag:* has_bank_guarantee (Boolean). If true, bypasses automatic 5% retention deductions.
 * **Situation de Travaux (Contractor Claim)**: The document submitted by the contractor claiming X\% progress.
 * **Certificat de Paiement (Architect Output)**: The approved financial document generated by the app, bound 1:1 to a validated *Situation*.
## 2. Core Landscape Scenarios to Code
### Scenario A: The Direct Single-Payment Flow (Small Trades)
Used for micro-lots or quick interventions where progress bills are unnecessary.
 * [ ] **Step 1:** Contractor submits a signed *Devis* \rightarrow App registers it as a Marché de Travaux (Status: Active).
 * [ ] **Step 2 (Optional):** Contractor requests an upfront deposit. They submit a *Facture d'Acompte*. The Architect logs this to trigger an *Acompte Payment Certificate*.
 * [ ] **Step 3:** Work completes. Contractor submits a *Facture Finale*.
 * [ ] **Step 4 (Architect Action):** Architect reviews the final amount against the initial contract + amendments. If correct, approves and issues the *Certificat de Paiement de Solde*.
### Scenario B: The Cumulative Progress Flow (Standard B2B BTP)
The core architecture requirement. Contractors bill monthly based on percentage of completion.
 * [ ] **Step 1:** Initial Marché de Travaux is established (e.g., €100,000).
 * [ ] **Step 2:** *Situation N°1* submitted at 20% progress. Architect validates, system generates *Certificat N°1* for €20,000 (minus deductions).
 * [ ] **Step 3:** *Situation N°2* submitted at 45% **total cumulative progress**.
 * [ ] **Step 4 (Architect Action):** Architect modifies the line items (e.g., determines real progress is only 40%). The app must calculate the delta based on the Architect's approved percentage, not the contractor's claim.
 * [ ] **Step 5:** System generates *Certificat N°2* billing *only* the delta between Cumulative Situation N°2 and Cumulative Situation N°1.
### Scenario C: Subcontractor Direct Payment (*Délégation de Paiement*)
Under French law (Loi de 1975), a registered subcontractor (*Sous-traitant agréé*) must be paid directly by the Client if their contract exceeds €600, even in private works.
 * [ ] **Step 1:** A Marché must allow the attachment of Subcontractor Lots tied to a specific Main Contractor.
 * [ ] **Step 2:** When the Main Contractor submits a *Situation*, they include the subcontractor's portion.
 * [ ] **Step 3 (Architect Action):** The app must allow the Architect to split the single *Situation* validation into two separate *Certificats de Paiement*:
   * *Certificate Subcontractor:* Paid directly to the sub's bank account.
   * *Certificate Main Contractor:* Paid to the main contractor (minus the subcontractor's share).
## 3. Math Engine & Financial Deductions Checklist
When the Architect generates a Certificat de Paiement, the math engine must process calculations sequentially using this exact pipeline:
```
[Gross Cumulative Work Approved (€)]
               │
               ▼
   Minus: [Cumulative Retenue de Garantie (5% if no Bank Guarantee)]
               │
               ▼
   Minus: [Cumulative Compte Prorata deduction (Site expenses, e.g., 1%)]
               │
               ▼
   Minus: [Amortization of Initial Deposit (Acompte Recovery)]
               │
               ▼
   = [Net Cumulative Authorized Amount]
               │
               ▼
   Minus: [Total Net Amount Already Certified in Previous Certificates]
               │
               ▼
   = [NET AMOUNT TO PAY THIS PERIOD (Excl. VAT)]
               │
               ▼
   Apply: [Contractor-Specific VAT Rate or 0% Autoliquidation Subcontractor Flag]
               │
               ▼
   = [FINAL CERTIFICATE TOTAL (Incl. VAT)]

```
### Critical Edge-Case Rules for the Code:
 * [ ] **Deduction State Persistence:** Deductions are *always* calculated on the cumulative gross total first, and then past net certificates are subtracted. Never calculate deductions on isolated periods, or rounding errors will compound.
 * [ ] **The 5% Holdback (*Retenue de Garantie*):** If Marché.has_bank_guarantee == false, deduct 5% from the gross validated work on every intermediate certificate. On the very final certificate (*Solde* or *DGD*), this holdback must remain flagged as "Withheld" unless the Architect explicitly checks a Release Holdback toggle.
 * [ ] **Deposit Recoupment (*Remboursement d'acompte*):** If an upfront deposit was paid, it cannot just vanish. The code must allow the user to define a repayment schedule (e.g., reclaim 20% of the deposit value on every subsequent certificate until exhausted, or reclaim it entirely once progress hits 70%).
## 4. State Machine for Document Tracking
To prevent references from getting "dropped" or lost when names change, enforce this strict internal state tracking machine:
```
[Draft Situation] ──(Contractor Submits)──> [Pending Architect Visa]
                                                    │
                                           (Architect Edits/Approves)
                                                    │
                                                    ▼
[Paid / Closed] <──(Client Logs Payment)── [Certificat de Paiement Issued]

```
 * **Rule:** Once a Certificat de Paiement is issued, the underlying validated data for that specific Situation must be **hard-locked** to preserve the audit trail. Any adjustments needed later must be corrected in the *next* sequential cumulative situation.
